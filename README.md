# Cakes by ELI

Уебсайт, конфигуратор на десерти, система за поръчки и административен панел
за бутиковата сладкарница **Cakes by ELI**, Плевен.

- Публичен сайт на български: начало, меню по категории, продуктови страници,
  галерия с лайтбокс, контакти с работно време.
- **Конфигуратор на десерти с жива визуализация** — клиентът избира форма,
  етажи, блат, крем, покритие, цвят, декорация и надпис, а SVG визуализацията
  се променя на живо, слой по слой.
- Поръчки в два режима: готов продукт от менюто или персонален десерт.
- Административен панел: поръчки, статуси, календар за изработка, продукти,
  категории, персонализации, галерия, съдържание на сайта, работно време,
  почивки и съобщения.
- **Реална интеграция с Еконт** — създаване на товарителница директно от
  поръчката, PDF етикет, проследяване.

## Стартиране

Изисква **Node.js 20.9+** (проектът е разработван на Node 21).

```bash
npm install
cp .env.example .env.local          # и попълнете стойностите
npm run admin:hash -- "ваша-парола" # генерира ADMIN_PASSWORD_HASH
npm run db:migrate
npm run db:seed
npm run dev
```

Сайтът тръгва на <http://localhost:3000>, административният панел е на
<http://localhost:3000/admin>.

> **Важно за разработка:** без `DATABASE_URL` приложението ползва вградена
> PGlite база (истински PostgreSQL, компилиран към WASM). Тя се отваря само от
> **един процес наведнъж** — спрете `npm run dev`, преди да пуснете
> `db:migrate`, `db:seed` или друг скрипт, и обратно. В продукция това не важи,
> защото там се използва истински PostgreSQL сървър.

## Променливи на средата

Пълният списък с обяснения е в [`.env.example`](./.env.example). Задължителните
за продукция са:

| Променлива | Задължителна | Описание |
| --- | --- | --- |
| `APP_URL` | да | Публичният адрес на сайта. Ползва се в имейлите, QR кода и метаданните. |
| `DATABASE_URL` | да (продукция) | Connection string към PostgreSQL. Ако липсва, се ползва вградената PGlite база — само за разработка. |
| `SESSION_SECRET` | да | Минимум 32 знака. Подписва администраторската сесия. В продукция приложението отказва да стартира без него. |
| `ADMIN_EMAIL` | да | Имейл на администраторския акаунт. |
| `ADMIN_PASSWORD_HASH` | да | Хеш на паролата — вижте по-долу. |
| `OWNER_NOTIFICATION_EMAIL` | да | Адресът, на който собственикът получава новите поръчки. |
| `EMAIL_PROVIDER`, `EMAIL_FROM`, `EMAIL_API_KEY` | да | Изпращане на имейли. |
| `ECONT_*` | ако се ползва доставка | Достъп и данни на подателя за Еконт. |
| `STORAGE_*` | по избор | Къде се пазят снимките. |

Приложението не се проваля мълчаливо при непълна конфигурация — липсващите
настройки се показват като предупреждение в горната лента на админ панела.

## База данни

Схемата е PostgreSQL и се управлява с **Drizzle ORM** и реални миграции в
папка [`drizzle/`](./drizzle).

```bash
npm run db:generate   # генерира нова миграция след промяна в src/db/schema.ts
npm run db:migrate    # прилага миграциите
npm run db:seed       # начални данни
npm run db:reset      # изтрива само локалната PGlite база
```

### Опции на seed скрипта

Seed скриптът е **идемпотентен** — по подразбиране само допълва липсващото и
никога не презаписва съдържание, което собственикът е редактирал.

| Флаг | Действие |
| --- | --- |
| _(без флаг)_ | Настройки, работно време, 10 категории, 10 вида десерти с пълни конфигуратори, демо продукти и демо галерия. |
| `--demo-prices` | Попълва примерни цени. **По подразбиране цените са празни**, за да не се показват измислени суми. |
| `--reset-config` | Пресинхронизира конфигураторите (изтрива групите, опциите и правилата на seed-натите видове десерти). |
| `--force-content` | Презаписва настройките на сайта и работното време. |
| `--no-demo` | Без демо продукти и демо галерия. |

Демо съдържанието е ясно маркирано (`isDemo`) и админ панелът предлага бутон
**„Премахни всички демо продукти“**.

## Административен достъп

Няма клиентски профили — клиентите поръчват като гости. Собственикът има
**един акаунт**, защитен така:

- паролата се съхранява само като **scrypt** хеш;
- сесията е случаен 32-байтов токен в **HttpOnly**, `SameSite=Lax` бисквитка,
  `Secure` в продукция; в базата стои само SHA-256 отпечатъкът, така че
  сесиите могат да се отменят и изтичане на базата не дава използваеми
  бисквитки;
- опитите за вход са ограничени по IP **и** по акаунт;
- всяка админ страница и всяко админ действие проверява сесията самостоятелно
  на сървъра — скриването на бутон не е авторизация.

Генериране на хеш:

```bash
npm run admin:hash -- "вашата-силна-парола"
```

Копирайте резултата в `ADMIN_PASSWORD_HASH` и пуснете `npm run db:seed` —
акаунтът се създава, ако още го няма. Самата парола не се записва никъде.

Смяна на паролата по-късно: генерирайте нов хеш, обновете променливата и
пуснете

```bash
npm run db:seed -- --force-admin
```

Флагът е задължителен нарочно. Без него seed-ът не пипа съществуващ акаунт — в
противен случай всеки деплой би връщал паролата към стойността в Render и би
отменял смяна, направена от собственика.

## Имейл

Приложението не говори директно с доставчик. Всичко минава през адаптер в
[`src/lib/email/`](./src/lib/email).

| `EMAIL_PROVIDER` | Поведение |
| --- | --- |
| `console` | Записва пълното писмо в сървърния лог и **честно отчита, че не е изпратено**. За разработка. |
| `resend` | Изпраща през HTTP API на Resend. Нужни са `EMAIL_API_KEY` и `EMAIL_FROM`. |
| `smtp` | Заготовка. Изисква инсталиране на `nodemailer` и попълване на `SMTP_URL`. |

Изпращат се три вида писма:

1. **до собственика** при нова поръчка — с всички избори и връзка към поръчката
   в админ панела;
2. **до клиента** — потвърждение, че запитването е получено;
3. **до клиента при промяна на статуса** — по избор на собственика, с отметка
   в екрана за статус.

Всеки опит се записва в таблицата `order_emails`, включително неуспешните, и се
показва в детайла на поръчката. Изпращането се случва **след** като поръчката е
записана, чрез `after()` на Next — провал на доставчика никога не губи поръчка.

## Съхранение на файлове

| `STORAGE_PROVIDER` | Поведение |
| --- | --- |
| `local` | Записва в `public/uploads`. Подходящо за разработка и за собствен VPS. |
| `s3` | Заготовка за S3-съвместимо хранилище. Изисква `@aws-sdk/client-s3` и `S3_*` променливите. |

При serverless деплой (Vercel и подобни) файловата система е временна — там
**задължително** използвайте външно хранилище.

Всички качвания се валидират **по съдържание, а не по разширение**: файлът се
проверява по магически байтове (JPG/PNG/WEBP), преименува се на случаен UUID и
се записва с контролирано разширение.

## Еконт

Интеграцията е реална и е тествана срещу демо средата на Еконт (създадена е
истинска демо товарителница с PDF етикет). Целият код е изолиран в
[`src/lib/econt/`](./src/lib/econt).

| Среда | Адрес |
| --- | --- |
| `demo` | `https://demo.econt.com/ee/services` |
| `production` | `https://ee.econt.com/services` |

### Превключване demo → продукция

Само през средата, **без промяна в кода**:

```env
ECONT_ENVIRONMENT="production"
ECONT_USERNAME="вашият-e-econt-потребител"
ECONT_PASSWORD="вашата-парола"
```

### Данни на подателя

```env
ECONT_SENDER_NAME="…"            # точното име на клиента в Еконт
ECONT_SENDER_PHONE="…"
ECONT_SENDER_AGENT_NAME="…"      # задължително при юридическо лице
ECONT_SENDER_CITY_ID="32"        # от номенклатурата на Еконт (Плевен = 32)
ECONT_SENDER_CITY_NAME="Плевен"
ECONT_SENDER_POST_CODE="5800"
ECONT_SENDER_STREET="ул. …"      # точно както е в номенклатурата
ECONT_SENDER_STREET_NUM="…"
# или, ако изпращате от офис:
ECONT_SENDER_OFFICE_CODE="…"
```

### Три неща, които лесно се бъркат

1. **Кодировка.** Заявките се изпращат с `Content-Type: application/json;
   charset=utf-8`. Без това Еконт „изяжда“ кирилицата и връща грешки, които
   сочат към грешното поле.
2. **Град и улица.** Еконт приема само населени места и улици от собствената си
   номенклатура, заедно с представката („ул.“, „бул.“). Затова формите в сайта
   не приемат свободен текст за тях, а търсят в реалния списък.
3. **Товарителницата струва пари.** Затова има преглед преди създаване, бутон
   „Изчисли цената“ (не създава нищо) и изрично потвърждение, ако за поръчката
   вече има активна товарителница. При неуспех поръчката **не** се отбелязва
   като изпратена — показва се причината от Еконт на четим български.

### Вътрешен QR код

Всяка поръчка има собствен QR код, който отваря `/order-summary/<токен>` — 
кратко обобщение за подготовка на пратката: какво има вътре, тегло, размери,
как да се носи. **Не съдържа лични данни на клиента** и е различен от баркода
на самата товарителница на Еконт. Токенът може да бъде подменен от админ
панела, с което старите разпечатки спират да важат.

## Архитектура

Модулен монолит на Next.js — без излишни услуги, без отделен бекенд.

```
src/
  app/
    (site)/          публичен сайт (начало, меню, галерия, контакти, поръчка)
    admin/
      login/         вход
      (panel)/       защитените административни екрани
      print/[id]/    лист за печат, без админ рамка
    api/econt/       търсене в номенклатурите на Еконт
    order-summary/   страницата зад вътрешния QR код
  components/
    ui/              бутони, полета, модал, тостове, бадж
    site/            хедър, футър, карти, галерия, structured data
    admin/           админ рамка, таблици, формуляри с действия
  features/
    configurator/    чиста логика на конфигуратора + SVG визуализатори
    order/           потребителският поток на поръчката
    orders/          снимка (snapshot) на поръчката
  lib/               среда, база, формати, валидация, имейл, хранилище, Еконт
  server/
    queries/         четене от базата
    admin/           админ действия (server actions)
    orders/          създаване на поръчка
    auth/            сесии
```

### Конфигураторът

Най-важното архитектурно решение: **конфигураторът е изцяло управляван от
данни**. Видът десерт носи групи (въпроси), групите носят опции (отговори), а
правилата казват кога нещо се показва или скрива.

- Една и съща чиста функция решава какво се показва **в браузъра** и какво се
  **приема на сървъра** — двете не могат да се разминат, така че подправена
  заявка не може да вкара опция, която потребителят никога не е виждал.
- Групите декларират `previewChannel`, опциите — `previewValue`. Визуализаторът
  не знае какво е „торта“; той чете канали. Затова **нова опция, добавена от
  админ панела, променя картинката без промяна в кода**.
- Визуализаторите живеят в `features/configurator/preview/` и се избират по име
  (`cake`, `eclair`, `cupcake`, `macaron`, `cookie`, `cakepop`, `generic`).
  Нов вид десерт може да преизползва съществуващ визуализатор (чийзкейкът
  ползва този на тортата) или да ползва универсалния, докато не му бъде
  написан собствен.

### Поръчки и историческа точност

Поръчката пази **снимка** на това, което е било поръчано — с прочетените на
български етикети. Ако след година преименувате „Шоколадов крем“, старата
поръчка продължава да казва каквото е казвала. Връзките към продуктите остават
по id, за да работят справките.

Създаването на поръчка е в **една транзакция** (номер, поръчка, прикачени
файлове, история на статусите), а номерът идва от атомен годишен брояч, така че
две едновременни заявки не могат да получат един и същ номер.

### Кеширане

Публичните страници се рендират на сървъра при всяка заявка и четат директно от
базата. Промяна в админ панела се вижда в сайта **веднага, без нов деплой**.

## Деплой в продукция

### Какво изисква приложението

| Изискване | Защо |
| --- | --- |
| Дълго живеещ Node процес | Имейлите се изпращат след отговора чрез `after()`; ограничението на опитите за вход и кешът на номенклатурите на Еконт живеят в паметта на процеса. |
| PostgreSQL | Вградената PGlite база е само за разработка. |
| Постоянно място за файлове | Качените от админа снимки на продукти и галерия. Диск или S3 — но **не** ефимерна файлова система. |
| Една инстанция (или споделен store) | Ограничението на опитите за вход е в паметта. При няколко инстанции го заменете със споделено хранилище. |

### Render (препоръчано)

Покрива и трите изисквания директно: истински Node процес, управляван
PostgreSQL и постоянен диск.

В хранилището има готов [`render.yaml`](./render.yaml) — създайте Blueprint от
него, попълнете променливите, отбелязани с `sync: false`, и деплойнете.

```
build:       npm ci && npm run db:migrate && npm run build
pre-deploy:  npm run db:migrate && npm run db:seed && npm run db:verify
start:       npm start
disk:        public/uploads   (за качените снимки)
```

Деплоят е напълно автоматичен — нищо не се пуска ръчно от Render Shell.

Миграциите са в **build** командата, защото `next build` чете от базата през
`generateMetadata()`; без тях билдът пада с `relation "site_settings" does not
exist`.

**Pre-deploy** попълва базата и я проверява, преди новата версия да поеме
трафик:

- `db:seed` е идемпотентен — създава само липсващото и никога не презаписва
  съдържание, редактирано от админ панела. Ако предишен опит е прекъснал по
  средата, повторното пускане дописва липсващите групи на конфигуратора.
  Админ паролата се задава само при създаване на акаунта; смяна се прави
  съзнателно с `npm run db:seed -- --force-admin`.
- `db:verify` проверява, че критичните таблици не са празни, и излиза с ненулев
  код, ако са. Render тогава задържа предишната версия вместо да пусне сайт без
  меню и без конфигуратор.

Демо снимките са в Git (`public/demo/`) и идват заедно с билда, затова
преживяват рестарт и нов деплой. Дискът се ползва само за качените от админа
файлове. `npm run demo:photos` е локален инструмент за обновяване на демо
снимките и **не** участва в деплоя.

> Безплатните планове на Render заспиват при бездействие и нямат постоянен диск,
> а безплатната база има срок на живот. За реален сайт е нужен платен план;
> проверете актуалните условия при тях.

### Netlify

Работи, но изисква преработка, защото функциите там са serverless с ефимерна
файлова система:

1. `STORAGE_PROVIDER=s3` и дописване на S3 адаптера в
   [`src/lib/storage.ts`](./src/lib/storage.ts) — иначе всяка качена снимка
   изчезва при следващия студен старт.
2. Външен PostgreSQL (Neon, Supabase).
3. Ограничението на опитите за вход трябва да мине към споделено хранилище —
   иначе всяка инстанция брои отделно и таванът реално се вдига.

### Ръчен деплой (VPS)

```bash
npm ci
npm run build
npm run db:migrate
npm start          # зад nginx/Caddy с TLS
```

### Задължителни настройки

1. **`DATABASE_URL`** към PostgreSQL.
2. **`SESSION_SECRET`** (32+ знака) и **`ADMIN_PASSWORD_HASH`**. Никога в git.
3. **`APP_URL`** — реалният домейн с `https://`; от него се строят връзките в
   имейлите и QR кода.
4. **Имейл** — `EMAIL_PROVIDER=resend` (или SMTP) + `OWNER_NOTIFICATION_EMAIL`.
5. **Еконт** — `ECONT_ENVIRONMENT=production` и реалните достъпи.

Проверка след деплой: отворете `/admin` — горната лента показва всяка липсваща
настройка.

## Какво остава от клиента

Тези неща съзнателно **не са измислени** и трябва да бъдат попълнени:

| Какво | Къде се попълва |
| --- | --- |
| Имейл адрес за контакт и за поръчки | Админ → Съдържание, и `OWNER_NOTIFICATION_EMAIL` |
| Реалният каталог продукти | Админ → Продукти (демо продуктите се махат с един бутон) |
| Реални цени | Админ → Продукти и Админ → Персонализации. Без цена сайтът показва „Цена след уточнение“. |
| Реални снимки | Админ → Продукти и Админ → Галерия (сега има собствени SVG илюстрации) |
| Състав и алергени | Админ → Продукти. Нищо не се предполага автоматично. |
| Потвърдено работно време | Админ → Работно време (сега са примерни стойности) |
| Юридическо лице, ЕИК, адрес на управление | Страница „Политика за поверителност“ — текстът е маркиран |
| Достъпи за Еконт (продукция) | `.env` |
| Условия за доставка и срокове за изработка | Админ → Съдържание |

Демо съдържанието е ясно отделено от потвърдените данни: маркирано е в базата,
показва се с бадж „Демо“ в админ панела и се премахва с едно действие.
